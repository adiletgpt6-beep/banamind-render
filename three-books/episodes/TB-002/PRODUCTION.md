# TB-002 — запуск и реализация

Рабочая ветка `feature/three-books-tb-002-tiko`; системная база `docs/three-books-production-system`. Не начинать производство в main или в ветке Нокса. В новом чате сначала проверить STATUS и фактический HEAD: работа могла уже продвинуться.

## Первый исполнимый шаг

Из корня репозитория:

```bash
python3 scripts/three-books/tb002/prepare_sources.py
```

Проверит архивы и распакованные байты всех трёх TXT, выведет доступные пути без содержимого и имён источников. Полные тексты окажутся в `.tb002-work/sources/S01.txt` … `S03.txt`, вне public. Прочитать внутренний SOURCE_MAP и привязанные разделы. Если проверка не прошла, исправить точную причину; не считать перенос книги состоявшимся только по имени файла.

## Техническая опора

Получить производственную ветку первого фильма через настроенный remote, не меняя её. Прочитать закреплённый коммит из REFERENCE.md. У него рабочие зависимости Python/NumPy/ModernGL/Mesa EGL, FFmpeg, инструменты ElevenLabs и Whisper. Начать с существующего решения, а не проектировать рендер с нуля. Копировать только необходимые технические части в собственные каталоги нового выпуска с сохранением разрешённых лицензий.

Новый runtime и постановка: `src/three-books/tb002/`. Инструменты: `scripts/three-books/tb002/`. Входные сценарные данные: папка выпуска. Чистая зрительская выдача при необходимости: `public/three-books/tb002/`. Сгенерированные промежуточные аудио, кадры и распакованные книги не добавлять массово в git.

Старый риг fox.py не является ригом Тико. Нарисовать отдельную карту частиц енота и Наи. Старый парсер 15×120 тоже заменить: SCENES.json содержит 44 сцены и 11 разных частей. Не притворяться, что декорации прежних глав — уже новый фильм.

## Последовательность

1. Проверить три источника, карту идей и готовую речь. Сохранить правки и собственный plain-text export без заголовков B/A.
2. Извлечь 65 исходных speech blocks, подготовить голосовой pilot. Зафиксировать фактические параметры и прослушанный/измеренный охват.
3. Сгенерировать финальную речь с кэшем по входам. Измерить блоки; привести окончательные границы сцен/частей к 1800 секундам без растягивания речи. Сохранить measured timeline, не подменять его предварительными таймкодами.
4. Сделать контрольный ролик открытия и фрагмент теста переноски; проверить силуэты, касания, текст, компрессию и голос. Исправить замеченные причины. Для пилота не ждать обязательного ответа владельца.
5. Рендерить только TB-002 по полуоткрытым интервалам кадров `[start,end)`, суммарно `[0,54000)`. Кадр вычисляется по абсолютному времени/seed. Сегменты хранить с хэшами и параметрами; возобновлять только отсутствующие или невалидные.
6. Свести голос, редкие эффекты и тишину, получить AAC; собрать faststart MP4. Проверить полный decode, кадры, формат, длительность и критические числа. Выборочный художественный просмотр не называть полным прослушиванием.
7. Создать пять настоящих обложек, контакт-листы, финальные метаданные и галерею. Проверить отсутствие внутренних источников во всём наборе.
8. Загрузить только проверенный разрешённый набор через приватный релиз **`tb-002-film`**, без изменения `nox-film`. Заполнить DELIVERY, QA, STATUS и реестр. Ссылки публиковать владельцу после проверки; YouTube не трогать.

## GitHub Actions

Собственный workflow `.github/workflows/three-books-tb002.yml` должен иметь узкие пути и явный запуск, например `[tb002:voice]`, `[tb002:pilot]`, `[tb002:render]`, `[tb002:assets]`. Метки — проектное соглашение для реализации, пока workflow ещё не создан. Не утверждать, что их уже можно запускать.

Документационный commit не должен вызывать ни TTS, ни рендер. CI публикации использует имеющийся доступ и secret `ELEVENLABS_API_KEY`, не новое платное подключение. Текущие ограничения Claude по Releases обходятся настроенным CI, как в первом фильме. Ключ не выводить и не запрашивать его значение.

Старый workflow имеет широкую загрузку `release/*`; такую логику слепо не переносить. У TB-002 должен быть явный allowlist финальных файлов. Исходные TXT, gzip, SOURCE_MAP, manifest приватных источников, QA с внутренними именами и рабочие каталоги в зрительскую выдачу не попадают. У QA для релиза — очищенная зрительская версия, внутренний полный отчёт остаётся в репозитории.
