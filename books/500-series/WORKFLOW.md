# BanaMind BM-001…BM-500 — операционная схема

> **Новый режим 2026-10-21:** см. `books/500-series/SOURCE_INGESTION.md`. При успешном подготовленном GitHub source pack пользователь отправляет вложение только ChatGPT, а в Claude Code — **одну короткую команду**, без файла. В `STATUS.md` точно различать `SOURCE_READY_IN_GITHUB` и `SOURCE_NOT_RECEIVED_IN_CLAUDE`. Правило «владелец должен передать файл отдельно в Claude» ниже остаётся только для старых/неразмещённых источников. После GitHub-верификации Claude читает книгу из `sources/BM-NNN/part-XX.txt` и начинает автономный продакшен.


## Кто за что отвечает
- **Владелец:** выбирает книгу, обеспечивает доступ к аудио/видео/PDF, сообщает право использования, длительность и утверждает бриф/пилот/финал (либо явно делегирует утверждение).
- **ChatGPT-координатор:** закрепляет следующий свободный BM-ID, составляет `tasks/BM-NNN/TASK.md` в GitHub с точным путём источника и критериями, выдаёт **короткий промпт** Claude, проверяет PR и документы, обновляет REGISTRY/HANDOFF после подтверждения фактов.
- **Claude Code-исполнитель:** читает GitHub-инструкции и одну задачу; создаёт сценарий и готовые материалы в своей ветке, обновляет свой STATUS, отдаёт PR и артефакты. Каждый свежий чат возобновляет ровно одну задачу.

## Приём новой книги
1. Владелец отправляет **один** источник (или несколько частей одной книги) и сообщает название, желаемую длительность/язык; право публикации и адаптации должно быть подтверждено до публичного релиза.
2. ChatGPT сверяет существующие BM-ID и активные PR; фиксирует следующий **RESERVED** номер. Имя slug — латиница, уникальное.
3. Источник: для PDF — страницы, для видео/аудио — таймкоды; проверки: доступ/размер/полнота/контрольная сумма. **Файл, загруженный в чат ChatGPT, сам по себе не становится доступен Claude Code или GitHub.** Перед задачей убедиться, что Claude реально получил вложение либо имеет защищённую ссылку на R2/GitHub Release/другое разрешённое хранилище. Если источник большой — владелец сам готовит подходящий размер или размещает в защищённом хранилище. Файлы > лимита Claude не передавать напрямую.
4. Создать `tasks/BM-NNN/TASK.md` по шаблону, `STATUS.md` по шаблону, branch `feature/banamind-bm-nnn-<slug>`, PR. Не дублировать ранее выданное задание.
5. Отправить пользователю короткую команду из [PROMPTS.md](PROMPTS.md). Claude должен **сам читать длинный промпт из GitHub**.

## Стадии и критерии приёмки
| Этап | Что должно существовать | Далее |
|---|---|---|
| SOURCE_READY | доступный источник и маркеры страниц/таймкодов; подтверждённые права или блок публикации | расшифровка |
| BRIEF_READY | карта фактов, тезисов, глав, длительность, спорные места | решение владельца |
| APPROVED | явное утверждение брифа | пилот |
| IN_PRODUCTION | сценарий, озвучка, анимация, тестовый фрагмент | QA |
| QA_REVIEW | полный проверенный MP4, SRT, пять обложек и метаданные | владелец |
| FINAL_APPROVED | подтверждение владельца и ссылки на исходники | публикация владельцем |
| PUBLISHED | реальная ссылка YouTube и дата (после публикации, не автоматически) | закрыть запись |
| BLOCKED | причина, что требуется для снятия блокировки | не тратить ресурсы |

## Параллельность и контекст
- Допустимы разные Claude-чаты **для разных книг**, у каждого своя ветка/PR/STATUS. Одну и ту же книгу одновременно двум Claude-чатам не поручать.
- **Не** массово запускать 499 книг пустыми промптами: только книги с реально полученными источниками.
- Промпты короткие: BM-ID + ссылки на README/MASTER/TASK/STATUS + указание продолжать из GitHub.
- Если окно контекста ChatGPT переполнится: новый ChatGPT читает `HANDOFF.md`, `REGISTRY.csv` и последнюю STATUS в GitHub (см. [PROMPTS.md](PROMPTS.md)); затем сам проверяет свежие PR. Не просить владельца пересказывать 500 книг.
- Если контекст Claude переполнится: он обновляет STATUS и коммитит, новый Claude запускается с тем же BM-ID. Не пытаться полагаться на память предыдущей сессии.
- Единственный источник истины для **общего прогресса** — merged ledger/реестр; PR branch STATUS может быть свежей, но не подтверждённой проверками. Отличать эти состояния.

## Защита от расходов и ошибок
- Один пилот перед полноценным рендером; отсутствующие зависимости, секреты API и сервисы отмечать как BLOCKED, не угадывать значения.
- Использовать существующий Remotion/release workflow, не копировать целиком пайплайн по 500 папкам, если возможна параметризация и тесты.
- Отдельные релизы для каждой книги; проверить доступность приватных ссылок перед выдачей.
- GitHub Actions артефакты имеют срок хранения; итоговые исходники и метаданные должны иметь устойчивую ссылку/бэкап.
- Не мерджить PR в обход подтверждения владельца; не запускать массовую публикацию на YouTube.
- Серийное массовое применение авторских материалов возможно только после проверки лицензии и правил площадки. Уникальный монтаж и 5 превью сами по себе не обеспечивают монетизацию.

## Схема папок
```
books/500-series/
  README.md  MASTER_CLAUDE.md  WORKFLOW.md  HANDOFF.md
  REGISTRY.csv  PROMPTS.md
  templates/TASK.md  templates/STATUS.md
  tasks/BM-002/TASK.md  (появится с новой книгой)
  tasks/BM-002/STATUS.md
books/<slug>/...         (существующая структура оригинального BanaMind)
src/books/<slug>/...
```

## Приёмка после PR
Координатор проверяет статус Actions, изменения файлов и ссылки. Только после реального подтверждения обновляет `REGISTRY.csv`, `HANDOFF.md`, следующий BM-ID. Мерджить базовый PR #121 раньше/в согласованном порядке: эта документация основана на его ветке.
